Article 1 · Questions 1, 2, 9, 10

MST regions are configuration domains, not automatic trunk groups

Multiple Spanning Tree reduces the number of spanning-tree instances by mapping many VLANs to a smaller set of MST instances. That efficiency depends on every switch in a region agreeing on three identity inputs: region name, revision, and the complete VLAN-to-instance mapping. A one-VLAN mapping difference changes the configuration digest even when the displayed name and revision look correct. The link becomes a region boundary, and the two regions interact through the Common Spanning Tree rather than sharing internal instance state.

Operational consequences

  • A VLAN can take an apparently irrational path because its instance has different roots or is represented only through the CIST across a boundary.
  • Bridge priority selects a root; it does not determine region membership.
  • Extreme defaults can leave each switch in a unique region until matching identifiers are configured.
  • Root Guard deliberately places a port into root-inconsistent when a superior BPDU arrives where the root must never appear.

Safe troubleshooting sequence

  1. Identify the VLAN and effective MST instance.
  2. Compare region name, revision, mapping, and digest on both ends.
  3. Check whether the port is internal or boundary and which bridge is root for the CIST and the affected MSTI.
  4. Correct the unintended root or region input; do not disable STP to make a blocked path forward.
Memory model: region identity answers “who shares the topology database?” Root priority answers “who wins inside that topology?” Treat them as separate questions.

Article 2 · Questions 3–5, 12–13

LACP, hashing, and multichassis state have different jobs

A standard LAG makes several physical links look like one logical interface. LACP validates that members belong to compatible actors and aggregators; it does not stripe every packet across every member. Most platforms select a member with a per-flow hash so packets in one flow remain ordered. Four 10-Gbps links therefore provide roughly 40 Gbps of aggregate capacity across many flows, while one ordinary flow may remain limited to one 10-Gbps member.

Multichassis designs add node redundancy, but they also add control channels. Juniper MC-LAG uses ICCP to exchange control and operational state and an ICL to carry data between peers. An up ICL does not prove ICCP is healthy. Arista MLAG similarly depends on its peer link and peer liveness; reload delay can hold downstream links until routing and neighbor state are ready. Cisco vPC distinguishes dual-attached vPC members from single-attached orphan ports. An orphan may need explicit suspend behavior during a peer-link failure. Aruba VSX uses an ISL plus keepalive and offers split controls for applicable non-MCLAG interfaces.

Evidence to separate

  • Physical link: carrier, errors, MTU, optics.
  • LACP member: actor/partner system ID, key, collecting/distributing state.
  • Peer control: ICCP, keepalive, consistency checks, peer role.
  • Peer data: ICL/peer-link forwarding and VLAN allowance.

Failure-timeline discipline

Record peer detection, member suspension, routing recovery, ARP/ND or MAC synchronization, downstream admission, and application recovery separately. A link that comes up before Layer 3 state is ready can create a short but real blackhole.

Official reading: Juniper MC-LAG Arista MLAG Cisco vPC Aruba VSX

Article 3 · Questions 6–8, 11

Split-brain protection must survive the failure it is meant to detect

When two devices present one logical system, loss of the inter-device fabric can leave both halves believing they are active. Duplicate gateway addresses, bridge MACs, LACP actors, and routing state can then cause loops or blackholes. A split detector must use sufficiently independent evidence and must have a deterministic loser.

Vendor examples

  • FortiSwitch: MCLAG split-brain detection can make one peer dormant. Configured priority decides first; equal priority falls back to numerical MAC behavior documented for the release.
  • HPE Comware: IRF Multi-Active Detection can use BFD, LACP, ARP, or ND mechanisms depending on platform. MAD places a losing fabric into recovery and prevents duplicate active forwarding.
  • Huawei: LACP preemption controls whether a recovered, more-preferred Eth-Trunk member replaces a currently active member. A preemption delay reduces churn.
  • Nokia SR OS: LAG thresholds can change IGP cost or operational state as capacity degrades.

Design questions

  • Does detection share the same conduit as the failed fabric?
  • Which node loses, and are downstream ports, SVIs, and routed interfaces treated consistently?
  • Does partial degradation merely reduce capacity, raise routing cost, or declare the entire LAG down?
  • Which configured cost wins when a dynamic degradation action and explicit IGP cost coexist?
Production rule: never test split brain with only control-plane pings. Drive bidirectional traffic and confirm which exact interfaces and gateways remain active.

Official reading: FortiSwitch MCLAG HPE BFD MAD Huawei LACP preemption Nokia LAG thresholds

Article 4 · Questions 14–17

OSPF adjacency state tells you which exchange failed

Do not treat “OSPF is down” as one failure. Down or Init points toward missing or one-way Hellos. A neighbor that reaches 2-WAY has bidirectional Hello visibility. On a broadcast segment, two DROTHERs normally stay 2-WAY and form full adjacencies only with the DR and BDR. EXSTART or EXCHANGE means the routers discovered each other but cannot complete Database Description negotiation or exchange.

MTU mismatch is a classic inter-vendor EXSTART cause because the larger interface MTU appears in DBD packets. Matching the real data-plane MTU is preferable to globally hiding the check. Other DBD failures include unicast reachability, filtering, sequence problems, or duplicate router IDs. A duplicate router ID is more than a cosmetic log: LSAs use the advertising router identity, so duplicate ASBR IDs can create external-LSA flood wars.

Hello compatibility

Compare area, Hello/dead intervals, authentication, stub flags/options, subnet/network type where applicable, and passive state. A capture of both directions is more valuable than one router's configuration alone.

Exchange compatibility

At EXSTART/EXCHANGE, check interface MTU and successful DBD/LSR/LSU transmission. Use large do-not-fragment tests where meaningful. Do not jump immediately to route policy; the LSDB has not synchronized yet.

Official reading: Cisco EXSTART troubleshooting Cisco duplicate router IDs RFC 2328

Article 5 · Questions 18–20, 23–25

An OSPF LSA in the database is not automatically an installed route

Route installation follows topology and resolution rules after flooding. Type-1 and Type-2 LSAs describe an area's topology. ABRs originate Type-3 summaries between areas and Type-4 reachability toward ASBRs. ASBRs originate Type-5 externals, while an NSSA ASBR originates Type-7 and an elected NSSA translator ABR produces eligible Type-5 advertisements for the rest of the domain.

External Type-1 metrics add the internal cost to the external metric. Type-2 prefers the external metric first and uses internal reachability as a tie-break. A nonzero forwarding address tells routers to forward toward that address rather than automatically toward the ASBR; failure to resolve it can prevent route installation even when the ASBR itself is reachable. Inter-area summary configuration belongs on the ABR, not merely on a router that redistributes routes. Conditional default origination should withdraw when the qualifying local route disappears, preventing a dead exit from continuing to attract traffic.

Four checks: Is the LSA present? Is the advertising router or forwarding address reachable? Does the path win the protocol calculation? Did the RIB and then the FIB accept it?

On Check Point Gaia, protocol route maps can override corresponding Portal filtering or redistribution configuration. A healthy OSPF-over-VTI adjacency therefore proves the transport and neighbor state, not that an export policy permits the prefix.

Official reading: RFC 2328 OSPF RFC 3101 NSSA Check Point route maps

Article 6 · Questions 21–22, 33

OSPFv3 runs per link; BFD accelerates detection, not every recovery phase

OSPFv3 retains familiar neighbor, flooding, DR election, area, and SPF concepts while separating topology from IPv6 prefix information more cleanly. Neighbors communicate with link-local addresses and form adjacency on a link. Different global prefixes do not by themselves prevent a link-local adjacency, although they may still reveal an addressing design error.

BFD supplies rapid liveness detection to a client protocol. When BFD declares Down, OSPF reacts, runs the necessary topology calculation, changes the RIB, and programs the FIB. Existing sessions or applications may then need their own retry or reconnection. Those stages have different clocks:

  1. Failure begins.
  2. BFD or the routing protocol detects it.
  3. The routing protocol withdraws/recalculates.
  4. The RIB selects and the FIB programs an alternate.
  5. Stateful devices and applications recover.
Interview trap: “BFD converged in 300 ms” is incomplete unless the measurement identifies whether 300 ms describes detection, routing, forwarding, or application recovery.

Official reading: Arista OSPFv3 RFC 5340 RFC 5880 BFD

Article 7 · Questions 26–28, 35

BGP chooses policy first, then progressively narrower tie-breakers

BGP does not select the geographically shortest path. It applies an ordered policy decision to valid, resolvable candidates. Exact ordering varies by implementation, but common early controls include vendor-local weight, LOCAL_PREF, local origination, AS_PATH length, ORIGIN, and MED before later eBGP/iBGP, IGP-next-hop cost, age, router ID, cluster length, or neighbor-address tie-breakers. This order explains why a longer AS path can win when its LOCAL_PREF is higher.

MED is deliberately subtle. Default behavior commonly compares MED among routes from the same neighboring AS. Deterministic MED groups paths by neighboring AS and makes comparison within each group repeatable. Always compare MED makes MED comparable across different neighboring ASes. These knobs solve different problems and can produce network-wide changes if deployed inconsistently.

AS-path prepending is an outbound advertisement technique used to make one external path look longer to remote networks. It is a hint, not a guarantee: remote LOCAL_PREF or other policy can dominate it. To influence the local enterprise's outbound choice, use an appropriate inbound policy such as LOCAL_PREF rather than prepending received routes without a clear model.

Official reading: Cisco BGP best path Juniper BGP policy RFC 4271

Article 8 · Questions 29–32, 40, 42

Received, valid, best, installed, and advertised are different BGP states

An update can be received yet rejected by policy. A permitted path can remain invalid because its protocol next hop does not resolve. A valid path can lose best-path selection. A best path can fail RIB installation because another source wins or because recursion fails. An installed route can still be absent from hardware during a programming fault. Finally, a best path is advertised only when outbound policy and protocol rules permit it.

Next hop and policy

iBGP normally preserves an eBGP-learned next hop. The core must either carry that external next hop or the edge must intentionally set next-hop self. Junos exact prefix matches do not automatically include more-specifics; prefix-length policy must state the range.

Route reflection and multipath

A route reflector normally selects one best path from its own IGP position. ORR, add-path, or topology-aware placement can expose a better client choice. ORIGINATOR_ID and CLUSTER_LIST prevent reflection loops. Multipath does not remove best-path selection: candidates must satisfy implementation-specific equivalence before more than one path enters the RIB/FIB.

Debug order: received → policy accepted → next hop resolved → best → RIB installed → FIB programmed → advertised. Never use one stage as proof of the next.

Official reading: Juniper BGP resolution Cisco ORR RFC 4456 route reflection FortiGate BGP

Article 9 · Questions 37–40

BGP on firewalls and cloud edges adds platform-specific admission gates

Protocol theory is portable, but implementation gates matter. On Check Point Gaia, an Established session with received updates does not guarantee acceptance; explicit inbound policy may be required and CLI route maps can take precedence over related Portal rules. On BIG-IP, the routing protocol is enabled per route domain and the relevant self IP must permit TCP/179. HA configuration synchronization does not mean every runtime routing state transition happened identically, so active and standby state must be checked independently.

On FortiGate, use BGP path output together with a route-table lookup for the protocol next hop. Firewall policy and NAT cannot repair an unresolved BGP next hop because the route is not yet eligible for forwarding. On Cloudflare Magic Transit BGP over GRE/IPsec, current service rules include CPE-initiated sessions, nonzero hold time, service-specific ASN constraints, and no BFD support; tunnel health checks remain a separate traffic-steering input. The BGP session, underlay tunnel, tunnel health monitor, learned route, and anycast prefix advertisement are not one state.

Security note: TCP MD5 on a BGP session is a protocol authentication control with documented limitations; it does not encrypt GRE traffic. Use IPsec when encryption is required.

Official reading: Check Point routing policy F5 dynamic routing Fortinet BGP Cloudflare Magic Transit BGP

Article 10 · Questions 34–36, 41

Aggregation, communities, and Graceful Restart trade precision for scale or continuity

A useful aggregate should have a defined dependency on component routes. If an unconditional discard route keeps an aggregate advertised after all real components disappear, the network continues attracting traffic it cannot deliver. Protocol-aware aggregation with specific-route suppression can reduce table size while withdrawing when no contributors remain. A discard route may still be needed to prevent loops, but its advertisement conditions must be intentional.

Communities attach policy meaning without changing the NLRI. NO_EXPORT limits advertisement beyond the AS or confederation boundary; it does not automatically remove the route from the local RIB or set LOCAL_PREF. Operators must preserve communities across the sessions where downstream policy needs them.

Graceful Restart lets a helper temporarily retain stale routes while a peer's control plane restarts. That is safe only if the restarting system continues forwarding or another mechanism prevents traffic from using a dead path. If forwarding state is lost, stale retention can turn a short control-plane restart into a blackhole. Validate GR and nonstop-forwarding behavior for the exact platform and failure type.

Official reading: RFC 4271 aggregation RFC 1997 communities Arista Graceful Restart guidance

Article 11 · Questions 43–45

IS-IS separates intra-area detail from inter-area reachability

Level 1 routers know their own area. Level 2 routers form the inter-area backbone, and L1/L2 routers connect the levels. An L1 router commonly follows a default toward an L1/L2 router advertising the attached bit. That default is only useful if the L1/L2 router still has working Level 2 reachability. A backbone failure can therefore create a dead-end default unless overload, attached-bit, or default-origination behavior tracks the failure correctly.

As with OSPF and BGP, an adjacency and LSDB entry do not guarantee a usable route. Address-family capability, topology, policy, routing-instance membership, recursive resolution, and RIB preference still matter. A route present in the IS-IS database may be inactive because the next hop exists only in another VRF.

Nokia SR OS can connect LAG degradation to IS-IS cost. A staged design can make a partially failed bundle less preferred before a lower threshold takes the logical LAG down. Because explicit IGP cost and dynamic threshold cost can have defined precedence, test the effective metric rather than assuming that configuration presence equals activation.

Official reading: RFC 1195 Integrated IS-IS Nokia protocol show commands Juniper routing instances

Article 12 · Questions 46–48

Distance-vector failures are about information scope and provenance

RIP uses hop count and treats 16 as infinity. After a failure, a loop can produce the visible count-to-infinity sequence as routers repeatedly believe a neighbor has a path. Split horizon, poison reverse, triggered updates, and hold-down behavior reduce exposure, but the small metric ceiling and periodic update model limit scale.

EIGRP's DUAL provides loop-free computation, yet a route can remain Active when a router queries a large domain and does not receive all replies before the active timer expires. Stubs and summarization create query boundaries: a leaf that cannot provide transit reachability should not be asked to search hundreds of downstream paths.

Mutual redistribution creates a different loop. A prefix learned from OSPF can enter BGP at site A, return to OSPF at site B, and compete with its original route. Control it with explicit default-deny prefix policy, provenance tags or communities, rejection of returning tags, and documented ownership/metric rules. Test normal, single-exit failure, inter-site partition, and recovery; a design that works only while every link is up is incomplete.

Official reading: RFC 2453 RIPv2 RFC 7868 EIGRP Check Point route policy

Article 13 · Questions 49–50

Hardware forwarding and stateful paths decide whether control-plane success matters

Broadcom switching silicon and network operating systems can program an ECMP group with several equal next hops, then select one next hop with a hash over packet fields. A healthy group can balance thousands of flows well while one elephant flow stays on one path. Before declaring ECMP broken, verify the hardware group, member state, hash inputs, and a many-flow test. Resilient hashing reduces unnecessary remapping after membership changes; dynamic load balancing may use additional congestion signals when supported by the exact ASIC and NOS.

Migration troubleshooting must distinguish the RIB from the FIB and both from stateful session ownership. Adjacencies can be Full and routes can be correct on the new core while return traffic still follows the old firewall. Different stateful devices see opposite halves of the flow, so neither has a complete session or consistent NAT state. The safest response is normally to pause or roll back the gateway cut, restore symmetry, and prove the bidirectional packet walk before expanding the change.

Cutover gates

  • Control plane: neighbor and route policy.
  • RIB/FIB: selected and programmed next hop.
  • Services: ARP/ND, MAC, NAT, security policy, and session sync.
  • Application: DNS, retries, persistence, and actual transaction success.

Rollback trigger

Define a measurable threshold before the change. “Routing looks fine” is not a success criterion when packets, sessions, or applications disagree.
